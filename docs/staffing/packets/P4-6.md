## Requirement (D215 ruling 4, quoted)

> `auto-orch` (an `auto` crew resolves each stage role through `lee-llm-router staff --mode
> auto --json` at playbook-author time with the class key derived by `staff --from-packet`
> on the backlog item, writes the chosen routes and the block into the playbook's routing
> mandate, and fails closed to the mission's last named crew with a recorded reason if the
> router is unavailable)

"Stage role" here means the three **governed** roles (`primary`/`reviewer`/`judge`,
`routing_authority.GOVERNED_ROLES`) that make up "the playbook's routing mandate" —
that exact term is `GovernedMandate`/`GovernedMandate.to_payload()` in
`routing_authority.py`, the module whose own docstring calls it "the playbook routing
mandate." The five cognitive-stage CLI workers (`envision`/`ideate`/`reconsider`/`score`/
`author`, `routing.VALID_ROUTED_STAGES`) are a different, non-router-addressable mechanism
(a `workers:` shell-command template keyed by name in `config/crews.yaml`, not a router route
id) and are out of this packet's scope — the `auto` crew borrows its cognitive-stage worker
set unchanged from a required `fallback_crew` (see below), and only the governed block is
dynamically resolved.

## Owner's-call design decisions (read first — implement exactly this)

These are this session's resolutions of design questions the sprint plan and D215 leave open,
recorded here rather than left for you to re-derive:

1. **`fallback_crew` is a new, required sibling key to `crew: auto`.** A mission opts in with:

   ```yaml
   routing:
     crew: auto
     fallback_crew: sol-low-glm-pi   # any real name in config/crews.yaml; not "auto"
   ```

   `fallback_crew` supplies (a) the cognitive-stage `workers`/`stages` map, used unconditionally
   (auto only ever touches the governed block), and (b) "the mission's last named crew" the
   ruling requires as the fail-closed target when the router is unavailable. `crew: auto`
   without `fallback_crew` is a `ValueError` at parse time (config.yaml field
   `routing.fallback_crew` is required when `routing.crew` is `auto`) — this is a config
   validity check, fails before any cycle runs, not a runtime router failure.

2. **Resolution happens once per cycle, at playbook-author time, cached to a cycle-scoped
   artifact file** — not at mission-config-parse time (no backlog item exists yet then) and
   not recomputed on every later read within the same cycle. The artifact is
   `<mission root>/cycle-reports/<cycle_id>/routing/auto-crew-mandate.json`, written by the
   Author LLM-function closures in `routing.py` (the one place that already holds both
   `mission` and the concrete `item: BacklogItem` — see "Where to call it," below) before the
   author prompt is rendered. Every later reader of the mandate for that same cycle
   (`authoring._governed_routing_findings`, `authoring._mandate_routes_for_generator`,
   `cycle._governed_routing_guard`) reads the same file rather than re-invoking the router,
   so "the block" and "the chosen routes" the ruling requires are identical everywhere they
   are consulted for one cycle.

3. **`preflight._check_routing_authority` is the one caller that cannot know the per-item
   mandate** (preflight runs before any cycle starts, before Score/Select picks an item — see
   its own docstring, "Resolve the governed routing mandate from configuration alone"). For
   `crew: auto` it reports the **fallback crew's** governed block (truthful: it is what auto
   uses when the router is unavailable, and the crew whose stage workers always run) with one
   added sentence noting the effective per-cycle mandate is resolved dynamically. This is a
   deliberate, narrow exception, not an oversight — do not try to give preflight a
   per-item answer it structurally cannot have.

4. **Router harness short id → auto-orch governed harness name.** `config/staffing/routes.yaml`
   in `lee-llm-router` (a sibling repo, not this one) spells harnesses `agy`, `claude`, `codex`,
   `opencode`, `pi`; every governed route in this repo (and agent-orch's harness registry, per
   `docs/staffing/phase4-contracts.md` §4) is named `antigravity_cli`, `claude_code`,
   `codex_cli`, `opencode_cli`, `pi_cli`. Define this exact fixed map in the new module (below)
   and nowhere else. `omp_cli` has no router-side counterpart today — absent from the map on
   purpose; a route id whose harness is not in the map resolves like a router-unavailable
   failure (fail closed to the fallback crew), never a guess.

## New module: `src/auto_orch/auto_crew.py`

```python
"""Dynamic ``auto`` crew: resolves the governed mandate per cycle via the router.

See docs/staffing/phase4-contracts.md §4 and decisions.md D215 ruling 4 (chief-of-staff repo).
"""

AUTO_CREW_NAME = "auto"

ROUTER_CLI_ENV = "AUTO_ORCH_ROUTER_CLI"  # shlex-split argv prefix override, for tests

# Router routes.yaml harness id -> this repo's governed harness name.
ROUTER_HARNESS_TO_GOVERNED = {
    "agy": "antigravity_cli",
    "claude": "claude_code",
    "codex": "codex_cli",
    "opencode": "opencode_cli",
    "pi": "pi_cli",
}

GOVERNED_ROLE_TO_ROUTER_ROLE = {"primary": "impl", "reviewer": "review", "judge": "judge"}
```

Required contents and behavior (write the real implementation; the above is the fixed data,
not a stub to leave unfinished):

- `default_router_argv() -> list[str]`: reads `os.environ.get(ROUTER_CLI_ENV)`; when set,
  `shlex.split()` it (tests point this at a fake CLI script, argv form, exactly like
  `AUTO_ORCH_CREWS_FILE` in `routing.py:146-157` is the analogous override-env-var pattern for
  the crews file); otherwise `["lee-llm-router"]` (the real binary is on `PATH` — confirmed
  installed at `/home/lee/.local/bin/lee-llm-router` on this host, an editable install of the
  `lee-llm-router` sibling repo; treat it exactly as `sys.executable -m agent_orch.main` is
  already treated in `cycle.py:1726-1761`'s `_run_verify_cli` — a subprocess seam, not a
  Python import, matching this repo's `AGENTS.md` "subprocess seam rule, B1" and the sibling
  P4-4 packet's identical choice for agent-orch even though `lee_llm_router` happens to be
  `pip install -e`'d into this repo's own `.venv` too).

- `write_backlog_packet(item: "BacklogItem", path: Path) -> None`: writes the minimal
  Markdown packet `lee_llm_router.staffing.derive_class.parse_packet` requires — only `Kind`
  and `Owned paths` are mandatory fields there (router repo,
  `src/lee_llm_router/staffing/derive_class.py:250-253`). Write exactly:

  ```
  # Auto-orch backlog item — {item.title}

  - Kind: impl
  - Owned paths: `.`
  ```

  `Kind: impl` is a fixed placeholder — every one of the three governed-role `staff` calls
  below passes an explicit `--role` override that supersedes it (the CLI's own contract:
  `--role` is "required by auto and bind, an explicit override with `--from-packet`" per
  `lee-llm-router staff --help`). `Owned paths: `.`` is a fixed placeholder for the same
  reason: this packet exists only to get a `class_key` string, and every other class
  dimension (`oracle_type`, `size_band`, `language`) is passed as an explicit CLI override
  below too, so no packet field but the two required ones needs to be truthful about specific
  files. Do not add a `Domain:` field — leave `domain_tags` to derive from the (empty)
  keyword-table match against `.`, which is a safe, deterministic `none`.

- `resolve_role_route(router_role: str, packet_path: Path, *, timeout_seconds: float = 60.0,
  argv_prefix: list[str] | None = None) -> RoleRouteResult`, where `RoleRouteResult` is a small
  dataclass with fields `staff_block: dict[str, Any]` (the full parsed `--json` payload, kept
  verbatim — this is "the block" the ruling requires persisted), `route_id: str`,
  `harness: str | None`, `model: str | None`, `effort: str | None`. Runs (argv list, no shell,
  exactly the `_run_verify_cli` pattern in `cycle.py:1726-1761`: `subprocess.run(
  capture_output=True, text=True, timeout=timeout_seconds)`, `OSError`/`TimeoutExpired` and a
  non-JSON/malformed stdout are all "unavailable"):

  ```
  <argv_prefix or default_router_argv()> staff --from-packet <packet_path> --role <router_role>
  --oracle-type none --size-band m --language mixed --mode auto --json
  ```

  On success (`returncode == 0`, stdout parses as a JSON object with a non-empty
  `selected_route` string), resolve `harness`/`model`/`effort` for that route id by also
  running `<argv_prefix> catalog explain --role <router_role> --class <class_derivation.class_key
  from the staff payload> --json` and reading the matching `route_id` entry's
  `harness`/`model`/`effort` keys from its `workers`/`eligible`/candidate list — **or**, more
  directly and with one fewer subprocess call, read those three fields straight off the
  `catalog dump`-shaped data already available: actually simplest and correct — add one more
  small router-side lookup is unnecessary. Instead, resolve harness/model/effort from the
  **selected route id string itself is not decodable** (route ids are opaque slugs, e.g.
  `agy-gemini-3-8-flash-high-gemini-sub`, not a reliable `harness-model-channel` parse). Do
  the lookup by shelling out once more to
  `<argv_prefix> catalog explain --role <router_role> --class <class_key> --json` and reading
  the object in its `workers` (or equivalently-shaped candidate list — inspect the live
  `--json` output once, exactly as this packet's own author did with
  `lee-llm-router doctor catalog explain --help`/`staff ... --json` to confirm field names
  before writing code) whose `route_id` equals `selected_route`, taking that entry's
  `harness`/`model`/`effort` string fields (present in the router's own `routes.yaml` schema —
  confirmed fields: `route_id`, `model`, `effort`, `harness`, `channel`, `usage_capture`,
  `status`; `effort` is sometimes absent — treat missing as `None`). Map the router harness id
  through `ROUTER_HARNESS_TO_GOVERNED`; an unmapped harness is treated exactly like "router
  unavailable" for this role (see below) — never a guessed harness.

  Any of the following makes this call "unavailable" for its role, with the specific reason
  string recorded (do not conflate them into one generic message): CLI not found (`OSError`),
  timeout, nonzero exit, unparseable JSON, missing/empty `selected_route`, or an unmapped
  harness from the second lookup.

- `resolve_auto_governed_mandate(mission: Any, cycle_id: str, item: "BacklogItem") ->
  "routing_authority.GovernedMandate"`: the orchestrating entry point.
  1. Requires `mission.config.routing.crew == AUTO_CREW_NAME`; raises `ValueError` otherwise
     (programmer error, not a runtime condition).
  2. Writes the packet to a temp file under
     `mission.root / "cycle-reports" / cycle_id / "routing" / "auto-crew-packet.md"`
     (creating the `routing` directory; mirrors `_invoke_json_worker`'s own artifact
     directory convention in `routing.py:988-990`).
  3. Calls `resolve_role_route` for all three governed roles
     (`GOVERNED_ROLE_TO_ROUTER_ROLE`). If **any** role's call is unavailable, the whole
     resolution fails closed: do not partially adopt the roles that did resolve. Build the
     `GovernedMandate` from `mission.config.routing.crew_governed` (the fallback crew's
     governed block — already loaded verbatim onto `RoutingConfig` by the parser change
     below) via the *existing* `resolve_governed_mandate` merge logic (call it directly,
     passing a routing config equivalent to the fallback view — simplest correct
     implementation: temporarily treat `routing_config.crew_governed` as the sole source,
     reusing `_route_spec_from_mapping` already in `routing_authority.py` — do not
     re-implement mapping parsing a second time; add a tiny internal helper in
     `routing_authority.py` if needed, e.g. `_mandate_from_governed_block(block: dict, *,
     crew: str | None, source: str) -> GovernedMandate`, refactored out of the body of
     `resolve_governed_mandate` so both the normal path and this fallback path share it).
  4. Write the artifact (schema below) to
     `mission.root / "cycle-reports" / cycle_id / "routing" / "auto-crew-mandate.json"`
     regardless of which branch was taken (router-resolved or fallback), so a reader always
     finds one file with an unambiguous `"source"` field. Directory/file write failures here
     must not raise past this function — log nothing fancy, just don't let an `OSError`
     writing the audit artifact turn a working resolution into a crashed cycle; the returned
     `GovernedMandate` is still correct even if the artifact could not be written (record this
     in the artifact schema's own presence/absence, not a new fail-open sentinel).
  5. Returns the resolved (or fallback) `GovernedMandate`.

  Artifact JSON schema:

  ```json
  {
    "schema_version": 1,
    "cycle_id": "...",
    "backlog_title": "...",
    "source": "router_auto" | "fallback_crew",
    "fallback_crew": "sol-low-glm-pi",
    "fallback_reason": null,
    "roles": {
      "primary": {"router_role": "impl", "route_id": "...", "harness": "...",
                  "model": "...", "effort": null, "staff_block": { ...verbatim... }},
      "reviewer": {...},
      "judge": {...}
    }
  }
  ```

  When `source == "fallback_crew"`, `roles` carries whatever partial data was obtained before
  the first unavailable role was hit (best-effort audit trail — never used to build the
  mandate itself in that branch) and `fallback_reason` names the exact failure (e.g.
  `"router unavailable for role 'reviewer': lee-llm-router staff exited 3: <stderr>"`).

- `load_auto_crew_mandate(mission: Any, cycle_id: str) -> "routing_authority.GovernedMandate |
  None"`: reads the artifact written above; `None` if it does not exist or fails to parse
  (callers fall back to their own default — see the `resolve_governed_mandate` change below).
  Build the returned mandate the same way step 3 above does, from `roles.*.harness/model/effort`
  when `source == "router_auto"`, or by re-deriving from `fallback_crew`'s governed block via
  the mission's `routing_config.crew_governed` when `source == "fallback_crew"` (do not trust
  a stale/hand-edited artifact's literal fallback content as authoritative over the mission's
  live config).
