# Packet P4-5c — persist worker output per attempt; parse judge/review verdicts

- Kind: `impl`
- Declared size: 3 files, at most 200 changed lines
- Owned paths: `src/lee_llm_router/staffing/run.py`, `tests/test_staffing_run.py`,
  `config/staffing/schema/attempt-record.schema.json`
- Requirement, from `docs/staffing/needs-lee.md` ("Phase 4 addition by Chief (2026-09-12):
  P4-5c persist worker output per attempt", quoted in full below — implement exactly this,
  nothing more):

  > `run` captures the worker's stdout for usage parsing but neither persists nor prints it,
  > so a judge review's verdict text is lost unless the caller watches the console. Packet
  > P4-5c: write worker stdout/stderr to
  > `~/.local/state/lee-llm-router/artifacts/<attempt_id>/` and record the path in the
  > attempt's `provenance`; for `--role review`/`judge`, parse a final `REVIEW VERDICT:
  > ACCEPT|REJECT` line into `verdict.outcome` as `judge_pass`/`judge_fail` (D214 carry-over).
  > Tests. Class `impl/deterministic/none/s/python`.

  Facts already confirmed by a read-only research pass this session — reuse these exactly,
  do not re-derive or rename them:

  - The worker dispatch path is `dispatch_route()` (`run.py:2286-2412`); it already decodes
    the captured child stdout/stderr into `DispatchOutcome.stdout` / `.stderr`
    (`run.py:433-434`, populated `run.py:2393`, `run.py:2408-2412`). This is the exact text to
    persist — do not re-capture or re-run the worker.
  - `build_attempt_record()` (`run.py:1251`) is called from `doctor.py:1730` inside
    `_run_run`'s `_execute_registered()` closure (`doctor.py:1676` on), after
    `dispatch_route()` returns (`doctor.py:1678`) and after the optional `run_oracle()` call.
    `attempt_id` is optional on `build_attempt_record` and generated internally by
    `_new_attempt_id()` (`run.py:1367`) when the caller does not supply one. To name the
    artifacts directory after the same id that lands in the record, generate the id once in
    `_execute_registered()` (or in `build_attempt_record`, restructured so the directory is
    written using the id it is about to return) — the directory name and
    `record["attempt_id"]` must always match; never write the artifacts directory under a
    different id than the one persisted to the ledger.
  - `provenance` already exists in the record as a plain dict (`run.py:1390-1402`:
    `source`, `recorded_by`, `source_refs`, `notes`). Add a new key, e.g.
    `provenance["worker_output_dir"]` (absolute path string), additive — do not rename or
    remove the existing four keys, and add a `notes` entry recording that the output was
    persisted (or, on write failure, that it was not — see the fail-open rule below).
  - The `~/.local/state/lee-llm-router/` state-directory convention is already established
    three times with the identical explicit-param -> file-env-var -> root-env-var -> default
    precedence: `ledger.py:82` (`DEFAULT_ATTEMPTS_DIR`) / `ledger.py:326-350`
    (`resolve_attempts_path`); `availability.py:29` (`DEFAULT_AVAILABILITY_DIR`) /
    `availability.py:287` (`resolve_availability_path`); `census.py:92`
    (`DEFAULT_RUNS_DIR`) with `RUNS_STATE_ROOT_ENV_VAR` / `RUN_REGISTRY_DIR_ENV_VAR`
    (`census.py:95,98`). Follow this exact precedence pattern for a new
    `DEFAULT_ARTIFACTS_DIR = Path("~/.local/state/lee-llm-router/artifacts")` and its own
    resolver (own env vars, e.g. `LEE_LLM_ROUTER_ARTIFACTS_FILE`/`..._STATE_ROOT`, named by
    analogy to the existing three, not reused from them) — tests must be able to redirect the
    artifacts root the same way existing tests redirect the attempts/availability/runs roots
    (grep each of those three test files for the pattern).
  - Write two files per attempt: `stdout.txt` and `stderr.txt` (or a single `combined.txt` if
    you judge that simpler — pick one and be consistent; document the choice in the new
    provenance note), directly from `DispatchOutcome.stdout` / `.stderr`, no truncation, no
    reformatting. Directory creation and file writes must never raise past this function: on
    any `OSError` (permissions, disk full, path too long), the run still completes and the
    ledger record is still written — set `provenance["worker_output_dir"]` to `null` (or an
    "unavailable" sentinel string, your choice, documented) and add a `notes` entry naming the
    write failure, mirroring the existing fail-open convention already used elsewhere in this
    file for cost/oracle facts. Persisting output is diagnostic, and must never be the reason
    a real attempt fails to land in the ledger.
  - **Verdict parsing for `--role review`/`--role judge`.** Confirmed by this session's
    research pass: there is no existing per-role stdout verdict parsing anywhere in the
    codebase, and the attempt record's top-level `verdict` field is currently always one of
    the three canonical oracle-derived strings `pass` / `fail` / `unverified`
    (`_oracle_verdict()`, `run.py:2634-2640`; enum `canonicalVerdict` in
    `config/staffing/schema/attempt-record.schema.json:1696-1704`). The needs-lee note names
    the target as `verdict.outcome`, but the real, current field is the flat top-level string
    `verdict`, not an object with an `.outcome` member — this is an imprecision in the
    original note, not a literal field path to construct. Implement it as an **additive
    extension of the existing flat `verdict` string**, not a new nested object: when
    `class_record["role"]` is `"review"` or `"judge"` (the existing
    `_INDEPENDENCE_APPLICABLE_ROLES` frozenset at `doctor.py:1018` names exactly this role
    pair — reuse it, do not redefine it), scan the worker's captured stdout
    (`DispatchOutcome.stdout`) for a final line matching exactly `REVIEW VERDICT: ACCEPT` or
    `REVIEW VERDICT: REJECT` (search from the end of stdout, e.g. the last non-blank line
    match; do not match the string anywhere earlier in the text, since a worker might quote
    or discuss the marker before its real conclusion). When found, the recorded `verdict`
    field is `"judge_pass"` (ACCEPT) or `"judge_fail"` (REJECT) instead of the oracle-derived
    value that would otherwise apply for that role. When absent (or the role is not
    review/judge), behavior is completely unchanged — the existing `pass`/`fail`/`unverified`
    oracle-derived value stands exactly as today. Add `"judge_pass"` and `"judge_fail"` to the
    `canonicalVerdict` enum in `attempt-record.schema.json` (additive; the three existing
    values and every other schema branch stay exactly as they are). Do not touch
    `agentOrchAttemptVerdict` — it is a disjoint, unrelated record kind.
  - This is additive in every dimension: no existing caller of `build_attempt_record`,
    `dispatch_route`, or the schema's other record kinds changes behavior for a role outside
    `review`/`judge`, and no existing attempt record in the ledger is revalidated or rewritten.
