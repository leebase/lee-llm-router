## Owner's-call design decisions (read first — implement exactly this)

`task_type` does not exist anywhere in `src/auto_orch/` today (confirmed by full-repo grep,
see `docs/staffing/phase4-contracts.md` §4); it is the name of an unrelated field
(`ExecutionIntent.task_type`) in the sibling `agent-orch` repo and is **not** reused or
imported from there — this packet introduces a new, same-named field local to this repo's own
observation schema, populated the same way (a derived class-key string), coincidence in name
only.

1. **Not persisted on `BacklogItem` / `backlog.md`.** `BacklogItem` already carries several
   sticky, once-set fields (`work_class`, `signature`, `age`, ...) maintained by
   `scheduling_policy.py`, which this session deliberately does not touch — it carries
   unrelated uncommitted work from another lane right now (`git status` in this repo shows
   `src/auto_orch/scheduling_policy.py` and its test file modified). `task_type` is instead
   derived **fresh, per cycle, at cycle-report-writing time**, from the `BacklogItem` object
   already in hand — cheap, fail-open, and it never touches `backlog.md`'s schema or parsing.
2. **Derivation point:** `_selected_backlog_item_for_report(context)` in `cycle.py:3664-3681`
   is the single function that turns the cycle's `context["select_result"]`
   (a live `BacklogItem`) into the dict that ends up as `cycle_report["selected_backlog_item"]`
   (written at `cycle.py:3593` and again at `cycle.py:4259-4286` — confirm both call sites
   still call this same function before you change it; do not duplicate its body). Add one new
   key, `"task_type"`, to the dict it already returns.
3. **Router call, memoized per cycle.** Add `derive_task_type(item, *, timeout_seconds=30.0,
   argv_prefix=None) -> str | None` to `src/auto_orch/auto_crew.py` (same module P4-6 added):
   writes the packet via the existing `write_backlog_packet(item, path)` (reuse verbatim — do
   not re-derive the Markdown shape) to a temp path, then runs (argv list, no shell, same
   `_run_verify_cli`-style subprocess pattern P4-6 already established in this module):

   ```
   <argv_prefix or default_router_argv()> staff --from-packet <packet_path> --role impl
   --oracle-type none --size-band m --language mixed --mode auto --json
   ```

   On success, return `payload["class_derivation"]["class_key"]` (confirmed present in the
   router CLI's own `_run_staff` handler,
   `~/projects/lee-llm-router/src/lee_llm_router/doctor.py`: `payload["class_derivation"] =
   derivation` where `derivation["class_key"]` is the five-segment canonical string). On any
   failure — `OSError`, timeout, nonzero exit, missing/malformed JSON, or a missing
   `class_derivation` key — return `None`. This must never raise past this function and must
   never block or fail a cycle; a `None` `task_type` is simply "unclassified," never a cycle
   error.

   `_selected_backlog_item_for_report` must **memoize** this per cycle rather than calling it
   twice (it is called from two places in the same cycle, `cycle.py:3593` and
   `cycle.py:4259`): cache the derived value on `context` itself, e.g.
   `context.setdefault("_derived_task_type", auto_crew.derive_task_type(selected))` computed
   once and read thereafter within the same `context` dict's lifetime — pick whatever exact
   key/shape reads cleanly against this file's existing `context` usage conventions (grep how
   other derived-once-per-cycle values are already cached on `context` in this file, if any,
   and follow that shape rather than inventing a new convention).

   **Optimization, not required for acceptance:** when `mission.config.routing.crew == "auto"`
   and this cycle's `cycle-reports/<cycle_id>/routing/auto-crew-mandate.json` artifact (P4-6)
   already exists, its `roles.primary.staff_block.class_derivation.class_key` is the exact
   same information already computed once this cycle for the governed mandate — reusing it
   avoids a fourth subprocess call. If you implement this, it must still fail open to the
   fresh `derive_task_type` call (not to `None`) when the artifact is absent, unreadable, or
   missing that nested key. If this adds meaningful complexity, skip it — the required,
   simpler path is calling `derive_task_type` unconditionally.

## Changes to `src/auto_orch/performance.py`

1. `task` object schema (`performance.py:81-90`, the block with
   `"required": ["backlog_title", "producer_role", "reviewer_role"]`): add a new **optional**
   property (do not add to `required` — old observations.jsonl rows and old summary.json files
   on disk predate this field and must remain schema-valid without a rewrite):

   ```python
   "task_type": {"type": ["string", "null"]},
   ```

2. `collect_observation` (`performance.py:1117`), the `"task"` dict literal at
   `performance.py:1243-1257`: add a sibling key mirroring `backlog_title`'s own exact
   read pattern (same source dict, same `isinstance` guard):

   ```python
   "task_type": (
       (cycle.get("selected_backlog_item") or {}).get("task_type")
       if isinstance(cycle.get("selected_backlog_item"), dict)
       else None
   ),
   ```

3. `summarize_observations` (`performance.py:514-574`): add a second, additive rollup
   dimension alongside the existing `groups` list — do not change `groups`'s existing grouping,
   membership, or any of its computed fields; every existing test asserting on `groups` must
   keep passing unmodified.

   Refactor the per-group statistics block (`performance.py:544-560`, the
   `sample = len(members)` … through the `groups.append({...})` call) into a small helper,
   e.g. `_group_stats(kind: str, members: list[dict], *, producer=None, reviewer=None,
   task_type=None) -> dict[str, Any]`, parameterized so the existing `groups` loop and the new
   one below both call it — do not duplicate the arithmetic a second time.

   Add a new grouping pass over the same `observations` list, keyed by
   `observation["task"].get("task_type")` (a `None` value maps to the literal string
   `"unclassified"` — never silently dropped from the rollup), producing a new top-level
   `by_task_type` list in the returned summary, sorted by task_type string
   (`"unclassified"` last), each entry shaped like one `groups` entry but with `"group_kind":
   "task_type"` and a new `"task_type": "<value or 'unclassified'>"` key instead of
   `producer`/`reviewer`.

   Add the matching **optional** schema block to `SUMMARY_SCHEMA` (`performance.py:154-219`):
   a new `"by_task_type"` key in `properties` (not `required` — same additivity reasoning as
   above), an array of objects shaped like the existing `groups` item schema
   (`performance.py:172-218`) but with `"group_kind": {"const": "task_type"}`,
   `"task_type": {"type": "string", "minLength": 1}` replacing `producer`/`reviewer`, and the
   same `sample_size`/`comparison_eligible`/.../`final_completion_rate` fields, reusing
   `$defs` where it already fits.
